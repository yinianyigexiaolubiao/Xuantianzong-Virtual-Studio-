# 玄天宗视觉资产历史归档

This archive preserves the recovered visual-development lineage without confusing historical images with current Canon geometry.

## Rule

A picture can be valuable for **style, hierarchy, composition, atmosphere or asset-design history** while still being wrong as a map.

Current topology/scale comes from V1.6.1 + current technical controls/registered locks. Historical PNG/JPEG outputs never override those controls by themselves.

## 2026-08-06 V1.6 visual spec sheets

Recovered:

- `玄天宗视觉母图总览.png`
- `玄岳仙宗全景设定图.png`
- an annotated `image-gen-1.png` V1.6 whole-sect overview

`玄岳仙宗全景设定图.png` is treated as a **misnamed/historical spec sheet**, because its actual content is Xuantianzong V1.6 material. Filename alone cannot establish Canon identity.

The spec-sheet lineage is valuable because it records intent such as:

- one large floating Xuantian Peak only;
- other major peaks grounded;
- Xuantian Peak as a heavy inverted natural mass;
- white jade + restrained gold + limited vermilion hierarchy;
- Twin Swords as the only routine ice-blue glow;
- no all-floating nine peaks, no mass disk islands, no globally blue/dark Western fantasy reading.

Some individual statements in old visual sheets were superseded later (for example older restrictions on high-tier beasts in ordinary filming). Always resolve them through the current authority stack.

## Current use policy

### May be inherited

- mood/light direction when not conflicting with current C1/G1;
- visual hierarchy;
- successful gate/sword/hall shape ideas that survive current controls;
- framing inspiration;
- evidence of rejected visual mistakes.

### Must not be inherited automatically

- five-peak layouts;
- straight heaven-stair/straight-axis readings;
- extra floating primary peaks/islands;
- incorrect building coordinates;
- old beast visibility rules;
- obsolete teal/blue/stone-dominant palettes;
- AI-invented labels or topology.

## Sync status

The exact historical PNG/JPEG bytes are direct File Library assets, but the current connector does not expose their raw bytes to GitHub. They are therefore registered as `FILE_LIBRARY_ONLY_BINARY`, not falsely marked mirrored.
